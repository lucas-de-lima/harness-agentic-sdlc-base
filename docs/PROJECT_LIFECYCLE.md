# Project Lifecycle

## Purpose

Define the end-to-end lifecycle from an inherited project specification to a completed Go system.

## Lifecycle

```text
LEGACY INPUT
    ↓
DISCOVERY
    ↓
NAMING
    ↓
DOMAIN UNDERSTANDING
    ↓
ARCHITECTURE
    ↓
HARNESS SPECIALIZATION
    ↓
BACKLOG
    ↓
IMPLEMENTATION
    ↓
VERIFICATION
    ↓
HARDENING
    ↓
RELEASE
    ↓
PORTFOLIO
```

## Durable outputs by phase

### Discovery

- Project Brief
- candidate product name
- domain summary
- identified uncertainties

### Architecture

- Architecture Decision
- ADRs
- architecture constraints

### Harness Specialization

- dedicated skills
- agent configuration
- project policies
- tool requirements

### Backlog

- GitHub Project
- Epic/Feature/User Story/Task hierarchy
- acceptance criteria
- dependencies

### Implementation

- source code
- tests
- infrastructure
- pull requests

### Verification

- test evidence
- review outcomes
- quality-gate results

### Release

- release-ready repository
- README
- operational instructions
- changelog/release notes when useful

### Portfolio

- polished public repository
- architecture explanation
- engineering decisions
- selected trade-offs

## Completion principle

A project is complete when its lifecycle reaches Release and all project-specific exit criteria are satisfied.

The Harness Base itself is complete when all required foundation phases and the pilot project prove the system usable.
